# コーヒーレンス

## 感想ではなく推定で、次の一杯を決める

ブリューイング競技の練習支援アプリ（オフライン動作 / PWA）

## 誰の、どんな課題か

**ブリューイング競技の選手**は、有限の資源のなかで意思決定を強いられる。

- 公式豆は **数百 g**。試行回数は数十杯が上限
- 練習時間も、本番の試技 **2回** も限られている
- それでも判断材料は「なんとなく美味しかった」という **記憶と感想** だけ

## 味の差ではなく **自分の採点のブレ**

同じ杯を2回飲んでも点は揺れる。
そのブレ幅を知らないまま比べても、差があるかは分からない。

## 解いた問題：4つの問いに数字で答える

| 問い | 答える仕組み |
| --- | --- |
| 何をもう試さなくてよいか | 効果量と95%CI、探索の打ち切り判定 |
| 次に何を試すか | OFAT の自動計画と感度マップ |
| 本番で何を死守するか | 項目別 σ と必要試行回数 |
| 2回の試技をどう賭けるか | 期待値・分散・目標超過確率 |

<!-- 0:45 — 4行を読み上げるだけ。深掘りは次の2枚で。 -->

## 独創性：自分の測定誤差 σ を測り、ブラインドを強制する

- 計画に **隠し重複**（同一レシピの別コード）を必ず混ぜる
- そのペアの採点差 d から `σ̂ = sd(d)/√2`。5ペア未満は事前分布へ縮小
- **σ を超えない差は「判定不能」** と表示し、勝手に解釈させない
- 採点画面にレシピを出さない。ダミー記述子で当て勘を検定。リビール後は変更不可

<!-- 0:55 — 「味覚の検出限界を選手ごとに実測して基準にする」が新しい点。後出しを実装で塞いだことも。 -->

---

## 独創性：総合は「点」ではなく比較で取り、本番の賭け方まで出す

- 絶対点が最も不安定な総合・バランスは **対比較のみ**で収集
- 情報量が最大になるペアを提示 → **Bradley-Terry** で強さを推定、CI はブートストラップ
- **推移律の破れ**（A>B, B>C, C>A）を検出して信頼度に反映
- 2回の試技の合計を正規近似し、**目標ライン超過確率**で「攻める / 守る」を選ぶ

## Supabase 活用：練習は端末、共有はクラウド、不正は DB で止める

- **Auth**（メール + PKCE）でアカウント。ログインは *豆友* 機能だけの前提条件
- `profiles` / `posts` を **RLS** で保護：読むのは誰でも、書き消しは本人の行だけ
- **Realtime** で他端末の投稿がその場で流れてくる
- 自動判定の結果を `posts.moderation` に持ち、**CHECK 制約**で `allowed = false` は INSERT 不可
- 環境変数が無いビルドでは自動でローカル保存に退避 → **オフラインの体験を壊さない**

<!-- 0:45 — クライアントを信用しない最後の砦をスキーマに置いた、が言いたいこと。migrations は SQL でレビュー可能。 -->

## Devin 活用：46 本の PR で機能を積んだ

- 1タスク = 1 PR、日本語のコミットメッセージでレビューしやすい粒度
- 統計エンジン（σ / Bradley-Terry / 効果量）と UI を **並行**で実装
- CI が **oxlint + tsc + vitest（29 tests）** を毎 PR で検証、GitHub Pages に自動デプロイ
- このスライドも Marp の Markdown として Devin に書かせている

## インパクト：限られた豆の価値が変わる

- 同じ豆量から **判断できる差の数**が増える（判定不能を判定不能と言えるから）
- 練習ログが感想から **再現可能な推定**になり、コーチや仲間と議論できる
- まず競技者、その先はカフェの品質管理や焙煎の官能評価にそのまま効く

**味の探索を、感想の蓄積から推定の積み上げに変える。**
