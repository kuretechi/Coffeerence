# コーヒーレンス

## 感想ではなく推定で、次の一杯を決める

ブリューイング競技の練習支援アプリ（オフライン動作 / PWA）

---

## 誰の、どんな課題か

**ブリューイング競技の選手**は、有限の資源のなかで意思決定を強いられる。

- 公式豆は **数百 g**。試行回数は数十杯が上限
- 練習時間も本番の試技も **限られている**
- それでも判断材料は「なんとなく美味しかった」という **記憶と感想** だけ

<!-- 出せる杯数が有限なので、1杯の情報量を最大化しないと間に合わない。 -->

---

<!-- _class: statement -->

## 「美味しかった気がする」の正体は、
## 味の差ではなく **自分の採点のブレ**

同じ杯を2回飲んでも点は揺れる。
そのブレ幅を知らないまま比べても、差があるかは分からない。

---

## 解いた問題：4つの問いに数字で答える

| 問い | 答える仕組み |
| --- | --- |
| 何をもう試さなくてよいか | 効果量と95%CI、探索の打ち切り判定 |
| 次に何を試すか | OFAT の自動計画と感度マップ |
| 本番で何を死守するか | 項目別 σ と必要試行回数 |
| 2回の試技をどう賭けるか | 期待値・分散・目標超過確率 |

---

## 着眼点①：自分の測定誤差 σ を測ってしまう

- 計画に **隠し重複**（同一レシピの別コード）を必ず混ぜる
- そのペアの採点差 d から `σ̂ = sd(d)/√2`
- 5ペア未満は事前分布 σ=1.0 へ縮小して過信を防ぐ
- **σ を超えない差は「判定不能」と表示する**

<!-- 味覚の差の検出限界を、選手ごとに実測して基準にする。 -->

---

## 着眼点②：ブラインドをアプリが強制する

- 採点画面にレシピ情報を出さない。杯はブラインドコードだけ
- フレーバー再認には **ダミー記述子** を混ぜ、当てにいっていないか検定
- 正体は **リビール** まで開示しない
- リビール後は採点変更を禁止し、削除・計画変更は **監査ログ** に残す

<!-- 「後出しで自分に都合よく解釈する」経路を実装で塞いだ。 -->

---

## 着眼点③：バランスと総合は「点」ではなく「比較」で取る

- 総合評価は絶対点が最も不安定 → **対比較**のみで収集
- 情報量が最大になるペアを提示（既に決着した組は聞かない）
- **Bradley-Terry**（MM 反復）で強さ θ を推定、CI はブートストラップ
- **推移律の破れ**（A>B, B>C, C>A）を検出して信頼度に反映

---

## 本番のための2枚：戦略とリハーサル

- **戦略**: 2回の試技の合計を正規近似し、目標ラインの **超過確率** で並べ替え。攻めるか守るかを分散で選ぶ
- **リハーサル**: 準備7:00 → 競技7:00 → 審査3:00 を自動遷移。Wake Lock と通知音つき
- **トレーニング**: 三点識別（二項検定・3-up/1-down ステアケース）で味覚そのものを鍛える

---

## Supabase 活用：練習は端末、共有はクラウド

- **Auth**（メール + PKCE）でアカウント。ログインは *豆友* 機能だけの前提条件
- `profiles` / `posts` を **RLS** で保護：読むのは誰でも、書き消しは本人の行だけ
- **Realtime** で他端末の投稿がその場で流れてくる
- 環境変数が無いビルドでは自動でローカル保存に退避 → **オフラインの体験を壊さない**

---

## Supabase 活用：不適切投稿を DB 制約で止める

- アプリ側の自動判定は利用者が無効化できない設計
- 判定結果を `posts.moderation` に保存し、**CHECK 制約**で
  `allowed = false` の行はそもそも INSERT できない
- 空投稿・文字数も DB 側の制約で拒否
- マイグレーションは `supabase/migrations/` に3本、SQL でレビュー可能

> クライアントを信用しない最後の砦をスキーマに置いた。

---

## Devin 活用：46 本の PR で機能を積んだ

- 1タスク = 1 PR、日本語のコミットメッセージでレビューしやすい粒度
- 統計エンジン（σ / Bradley-Terry / 効果量）と UI を **並行**で実装
- CI が **oxlint + tsc + vitest（29 tests）** を毎 PR で検証
- Supabase 連携の衝突解消や、UI の細かな詰め（トグル化・遷移追加）まで委譲

---

## アーキテクチャ：オフラインファースト + 必要な部分だけクラウド

- React 19 + TypeScript + Vite、状態は **Dexie（IndexedDB）**
- Service Worker で資産をキャッシュし、通信なしで全機能が動く
- 統計は `src/lib` に純関数で分離 → テストが速く、結果を検証できる
- Supabase は **投稿と認証だけ**。練習データは端末から出ない

---

## 完成度：実際に動く一周がある

計画 → 抽出 → ブラインド採点 → 対比較 → リビール → 分析 → 戦略

- 抽出モードは注湯タイマー・TDS・**収率と 150mL 判定**まで実測
- JSON / CSV 書き出しでデータは持ち出せる
- GitHub Pages に自動デプロイ、PWA としてインストール可

---

## インパクト：競技者の「限られた豆」の価値が変わる

- 同じ豆量から **判断できる差の数**が増える（判定不能を判定不能と言えるため）
- 練習ログが「感想」から **再現可能な推定**になり、コーチや仲間と議論できる
- 対象はまず競技者、その先はカフェの品質管理や焙煎の官能評価にそのまま効く

---

## デモの流れ（3分）

1. セッション計画：因子を選ぶと杯数・隠し重複・提供順が出る
2. ブラインド採点：レシピが見えないまま採点、ダミーも混ざる
3. 対比較 → リビール：σ への寄与と正体が同時に出る
4. 分析：効果量と CI、「判定不能」の表示
5. 豆友：投稿が別端末に即時反映（Supabase Realtime）
